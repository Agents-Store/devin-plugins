# SQLAlchemy 2.1

Reference for SQLAlchemy 2.1: which version to install, what changed from 2.0, and a migration checklist. SQLAlchemy 2.1.0 was released on 2026-09-24; this page was checked against 2.1.3 (2026-10-03). The 2.0 series is still maintained (2.0.54, 2026-09-15). Source: [What's New in SQLAlchemy 2.1](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html). Re-check it when 2.1 reaches a new minor release.

The typed 2.0 style used across this plugin (`DeclarativeBase`, `Mapped`, `mapped_column`, `select()`) runs on 2.0 and 2.1 unchanged. The items below are the places where 2.1 behaves differently.

## Which Version to Install

| Situation | Install |
|-----------|---------|
| New project, plain SQLAlchemy, Python 3.11+ | `pip install "sqlalchemy>=2.1"` |
| Flask-SQLAlchemy 3.1.x | `pip install Flask-SQLAlchemy "SQLAlchemy<2.1"` |
| Python 3.10 or older | `SQLAlchemy<2.1` (2.1 requires Python 3.11+; 2.0 runs on 3.7+) |
| Alembic 1.20 | Python 3.10+ and SQLAlchemy 2.0+ (SQLAlchemy 1.4 is no longer supported) |

Flask-SQLAlchemy 3.1.1 (latest as of 2026-10, released 2023-09) declares `sqlalchemy>=2.0.16` with no upper bound, so a plain `pip install` resolves 2.1. A `MappedAsDataclass` base fails on 2.1 with `InvalidRequestError ... is already a dataclass` when `SQLAlchemy(model_class=Base)` is created ([pallets-eco/flask-sqlalchemy#1420](https://github.com/pallets-eco/flask-sqlalchemy/issues/1420), open); a plain `DeclarativeBase` works, so the pin is a precaution. Pin `SQLAlchemy<2.1` in `requirements.txt` / `pyproject.toml` too, and re-check the issue before dropping it. Plain SQLAlchemy projects, and Flask apps that use [Flask-SQLAlchemy-Lite](https://flask-sqlalchemy-lite.readthedocs.io/en/stable/) instead, are not affected.

## Migration Checklist: 2.0 to 2.1

Run the test suite on 2.0.x first with deprecation warnings turned into errors, fix what it reports, then upgrade:

```toml
# pyproject.toml
[tool.pytest.ini_options]
filterwarnings = [
    "error::sqlalchemy.exc.SADeprecationWarning",  # includes LegacyAPIWarning
]
```

1. **Python 3.11 or newer.** 2.1 dropped Python 3.10. `pip` on an older interpreter silently resolves the 2.0 series.

2. **PostgreSQL driver is psycopg 3.** A URL without a driver (`postgresql://...`) now means `psycopg`, not `psycopg2`. Name the driver explicitly:

   ```python
   from sqlalchemy import create_engine

   engine = create_engine("postgresql+psycopg://user:password@host/dbname")  # preferred, works on 2.0 and 2.1
   # engine = create_engine("postgresql+psycopg2://user:password@host/dbname")  # psycopg2 stays supported
   ```

   Install the driver with `pip install "psycopg[binary]"`. On 2.1 the `sqlalchemy[postgresql]` extra also installs psycopg 3; on 2.0 that extra installs psycopg2, so name the package directly. With the driver missing, `create_engine` raises `ModuleNotFoundError: No module named 'psycopg'` on 2.1 (`'psycopg2'` on 2.0). Other drivers changed too: Oracle's default is now `python-oracledb`.

3. **asyncio needs an extra.** `greenlet` is no longer installed by default: `pip install "sqlalchemy[asyncio]"`. Without it, `import sqlalchemy.ext.asyncio` raises `ImportError`.

4. **Autoflush is unconditional.** 2.0 flushed pending objects before ORM statements only; 2.1 flushes before every execution, including `text()` and Core statements. Code that added an object and then ran raw SQL expecting the old state now sees the new row. Use `with session.no_autoflush:` where the old behavior was intended.

5. **`Select.filter_by()` searches every FROM entity.** 2.0 applied it to the last joined entity (so `select(User).join(Address).filter_by(id=5)` silently filtered `Address.id`). 2.1 searches all entities in the FROM clause and raises `AmbiguousColumnError` when a name such as `id` exists in several. Use `.where(Entity.column == value)` after any join. The legacy `Query.filter_by()` is unchanged.

6. **Loader options on a deeper path.** When one object is loaded twice in a query (for example `joinedload(A.b).joinedload(B.a).raiseload("*")`), 2.1 applies the options of the shallowest path to later lazy loads. In 2.0 the winner depended on the loader strategy. Re-test queries that stack `raiseload` or `lazyload` on overlapping paths.

7. **Named types belong to `MetaData`.** `Enum` and PostgreSQL `DOMAIN` types inherit `MetaData(schema=...)`: with `MetaData(schema="myschema")`, `CREATE TYPE` is emitted as `myschema.status_enum` (2.0 emitted `status_enum`). `Table.drop()` no longer drops named types, `MetaData.drop_all()` does after the tables, and `CheckFirst` controls which existence checks run. `inherit_schema=` is deprecated: set `Enum(schema=...)` instead. Review autogenerated Alembic migrations for these types.

8. **Mapped dataclasses (`MappedAsDataclass`).** Defaults are no longer placed in `__dict__`: they are delivered when the attribute is read, so `Parent(related_id=5)` now inserts `related_id=5` (2.0 inserted `NULL` because `related=None` won). `relationship(default=...)` accepts only `None`; for collections use `default_factory=list`. In a `mapped_column()`, `default=` and `insert_default=` are mutually exclusive (2.0 accepted both). Flask-SQLAlchemy 3.1 cannot create a `MappedAsDataclass` base on 2.1 (see above).

9. **`composite()` returns an object.** A pending object's composite attribute used to read as `None` when every column was `None`; it now returns the composite class with `None` fields. Pass `return_none_on=` to restore `None`.

10. **`JSON.contains()` is deprecated.** It did a `LIKE` substring match on JSON text and now emits `SADeprecationWarning`. Cast for an explicit string match (`type_coerce(Model.data, String).contains(...)`) or use PostgreSQL `JSONB`, whose `contains()` is native JSON containment.

11. **Typing.** Statements and rows are typed `Select[int, str]` and `Row[int, str]` instead of `Select[Tuple[int, str]]`, so a `Row._t` workaround can be removed. Mypy 1.7 or newer is required.

## New in 2.1

Optional features; none are needed to run 2.0 code on 2.1.

- **Session-level execution options.** `Session(engine, execution_options={"schema_translate_map": {None: "tenant_a"}})` applies the options to every statement of the session, including flushes and eager loads. `sessionmaker`, `scoped_session` and the async variants accept it too.
- **`back_populates` takes the attribute.** `relationship(back_populates=Address.user)` or `back_populates=lambda: Address.user` instead of a string, so linters and type checkers can see the link.
- **`tstring()` for Python 3.14+.** Builds a statement from a template string; interpolated Python values become bound parameters, never SQL text. Treat it as a safer spelling of `text()`:

  ```python
  from sqlalchemy import tstring

  user_id = 42
  stmt = tstring(t"SELECT id, name FROM users WHERE id = {user_id}")
  # renders: SELECT id, name FROM users WHERE id = :param_1
  ```

- **`CREATE VIEW` and `CREATE TABLE AS SELECT`** constructs in Core.
- **`mssql-python` driver** for SQL Server (`mssql+mssqlpython://`), and `JSONB` for SQLite.

## Alembic Notes

Alembic 1.20 (2026-09-11) requires SQLAlchemy 2.0 or newer and Python 3.10 or newer, and works with 2.1. Settings can live in `pyproject.toml` (`alembic init --template pyproject`, Alembic 1.16+), `alembic check` (1.9+) fails CI when the models and the migrations disagree, and `file_template` accepts directory separators (1.18+). Commands: the `cli-recipes` skill.
